# Design: OpenMP Target SPIR-V Path for AMDGPU

## Overview

This document describes the design for enabling OpenMP offloading to AMDGPU via
SPIR-V as an intermediate representation. Device code is compiled to portable
SPIR-V at compile time; at runtime, AMD's comgr library translates SPIR-V to
native AMDGPU code for the actual GPU present.

This enables **portable fat binaries** — compile once, run on any AMD GPU —
while preserving the existing native compilation path for cases where the target
GPU is known.

```
COMPILE TIME (clang driver + clang-linker-wrapper):
  Source
    → Clang frontend (spirv64-amd-amdhsa triple)
    → LLVM IR
    → SPIR-V backend (llc)
    → SPIR-V binary
    → Embedded as device image in host binary

RUNTIME (AMDGPU offload plugin):
  Host binary loads
    → detect SPIR-V image (magic 0x07230203)
    → comgr: SPIR-V → LLVM bitcode (SPIRV-LLVM-Translator)
    → comgr: LLVM bitcode → AMDGPU relocatable (.o)
    → comgr: relocatable → executable code object
    → HSA loads native code object
    → execute on GPU
```

Both paths coexist: `--offload-arch=gfx90a` produces native ELF directly;
`--offload-arch=amdgcnspirv` produces portable SPIR-V.

## Component Design

### 1. Driver — Toolchain Selection

**File:** `clang/lib/Driver/Driver.cpp` (`getOffloadToolChain`)

**Problem:** `--offload-arch=amdgcnspirv` maps to triple `spirv64-amd-amdhsa`.
The OS is `AMDHSA`, so the OS-based switch runs first and creates
`AMDGPUOpenMPToolChain` (wrong — that toolchain is for native `amdgcn`). The
arch-based switch (which correctly routes to `SPIRVOpenMPToolChain`) never
executes.

**Solution:** Add a `Target.isSPIRV()` guard inside the `AMDHSA` case for
OpenMP:

```cpp
case llvm::Triple::AMDHSA:
  if (Kind == Action::OFK_HIP)
    TC = std::make_unique<toolchains::HIPAMDToolChain>(...);
  else if (Kind == Action::OFK_OpenMP) {
    if (Target.isSPIRV())
      TC = std::make_unique<toolchains::SPIRVOpenMPToolChain>(...);
    else
      TC = std::make_unique<toolchains::AMDGPUOpenMPToolChain>(...);
  }
  break;
```

The HIP path is left unchanged — `HIPAMDToolChain` already handles spirv64
internally for HIP workflows.

**Triple derivation path:**

```
--offload-arch=amdgcnspirv
  → inferOffloadToolchains(): OffloadArch::AMDGCNSPIRV → "spirv64-amd-amdhsa"
  → getOpenMPTriple("spirv64-amd-amdhsa"): vendor/OS known, returned as-is
  → getOffloadToolChain(): OS=AMDHSA, isSPIRV()=true → SPIRVOpenMPToolChain
```

### 2. SPIRVOpenMPToolChain Enhancements

**Files:**
- `clang/lib/Driver/ToolChains/SPIRVOpenMP.h`
- `clang/lib/Driver/ToolChains/SPIRVOpenMP.cpp`

**Inheritance:** `SPIRVOpenMPToolChain` → `SPIRVToolChain` → `ToolChain`

The toolchain is enhanced with AMD-aware functionality by delegating to the host
toolchain where appropriate (mirroring `AMDGPUOpenMPToolChain`'s pattern):

| Method | Behavior |
|--------|----------|
| `getAuxTriple()` | Returns host toolchain triple |
| `TranslateArgs()` | Delegates to host, binds `-march` from BoundArch |
| `addClangTargetOptions()` | Delegates to host, adds OpenMP device RTL |
| `addClangWarningOptions()` | Delegates to host |
| `GetCXXStdlibType()` | Delegates to host |
| `AddClangCXXStdlibIncludeArgs()` | Delegates to host |
| `AddClangSystemIncludeArgs()` | Delegates to host |
| `AddIAMCUIncludeArgs()` | Delegates to host |
| `getSupportedSanitizers()` | Delegates to host |
| `computeMSVCVersion()` | Delegates to host |

**Device libraries:** AMD device libs (ockl, ocml, etc.) are compiled as AMDGPU
bitcode and cannot be linked into SPIR-V at compile time. They are handled at
runtime by comgr after SPIR-V → LLVM IR translation. The only compile-time
library needed is the OpenMP device RTL, which the existing
`addOpenMPDeviceRTL()` handles.

### 3. Frontend — OpenMP CodeGen for SPIR-V

No code changes required. The SPIR-V backend's AMD mode
(`spirv64-amd-amdhsa`) handles address space mapping and calling conventions.
OpenMP runtime function calls and kernel entry points use the correct
conventions because the SPIR-V backend translates them from the generic LLVM IR
generated by the OpenMP frontend.

Areas verified:
- `SPIR_FUNC` / `SPIR_KERNEL` calling conventions are applied by the backend
- Address space numbering differences between SPIR-V and AMDGPU are handled by
  the SPIR-V backend's AMD-specific address space map
- `#pragma omp target` regions produce valid SPIR-V-compatible IR

### 4. Linker-Wrapper — SPIR-V Image Generation

**File:** `clang/tools/clang-linker-wrapper/ClangLinkerWrapper.cpp`

No code changes required. The existing paths already handle spirv64 correctly:

- `linkDevice()`: `spirv64` routes to `generic::clang()`
- `generic::clang()`: does not add `-flto` for spirv64, skips `--no-undefined`,
  adds `-march=amdgcnspirv`
- Output SPIR-V binary has the standard magic bytes (`0x07230203`) for runtime
  detection

### 5. Plugin Interface — SPIR-V Detection

**Files:**
- `offload/plugins-nextgen/common/include/PluginInterface.h`
- `offload/plugins-nextgen/common/src/PluginInterface.cpp`

**Change in `GenericDeviceTy::loadBinary()`:** A new branch detects
`file_magic::spirv_object` and calls the virtual `compileSPIRVImage()`:

```cpp
if (identify_magic(InputTgtImage) == file_magic::bitcode) {
  // existing JIT path via Plugin.getJIT().process()
} else if (identify_magic(InputTgtImage) == file_magic::spirv_object) {
  // NEW: compile SPIR-V via device-specific handler
  auto CompiledOrErr = compileSPIRVImage(InputTgtImage);
  // ...
} else {
  // existing raw buffer path (ELF, etc.)
}
```

**New virtual method in `GenericDeviceTy`:**

```cpp
virtual Expected<std::unique_ptr<MemoryBuffer>>
compileSPIRVImage(StringRef SPIRVImage) const;
```

Default implementation returns an error ("SPIR-V compilation is not supported
by this plugin"). Plugins that support SPIR-V override this method.

### 6. AMDGPU Plugin — comgr Integration

**File:** `offload/plugins-nextgen/amdgpu/src/rtl.cpp`

`AMDGPUDeviceTy` overrides `compileSPIRVImage()`:

```cpp
Expected<std::unique_ptr<MemoryBuffer>>
compileSPIRVImage(StringRef SPIRVImage) const override {
  Comgr.init();  // lazy dlopen of libamd_comgr.so
  std::string ISAName = "amdgcn-amd-amdhsa--" + ComputeUnitKind;
  return Comgr.compileSPIRV(SPIRVImage, ISAName);
}
```

The method uses `ComputeUnitKind` (e.g., `gfx90a`) which is populated during
device initialization from `HSA_AGENT_INFO_NAME`. The ISA name format
`amdgcn-amd-amdhsa--<gpu>` matches what comgr expects.

**Member:** `mutable ComgrInterface Comgr` — lazy-initialized, thread-safe.

### 7. comgr Interface — dlopen Wrapper

**File:** `offload/plugins-nextgen/amdgpu/src/ComgrInterface.h` (new)

A self-contained header that:

1. **Declares comgr types and enums** matching `amd_comgr.h` — avoids requiring
   the comgr header at build time.

2. **Loads `libamd_comgr.so` via dlopen** on first use (`std::call_once`).
   All function pointers are resolved via `dlsym`.

3. **Provides RAII wrappers** for comgr objects (`DataSetRAII`, `ActionInfoRAII`,
   `DataRAII`) to ensure proper cleanup.

4. **Implements `compileSPIRV()`** — the full comgr action chain:

```
Input SPIR-V binary
  → AMD_COMGR_ACTION_TRANSLATE_SPIRV_TO_BC     (SPIR-V → LLVM bitcode)
  → AMD_COMGR_ACTION_CODEGEN_BC_TO_RELOCATABLE (bitcode → .o)
  → AMD_COMGR_ACTION_LINK_RELOCATABLE_TO_EXECUTABLE (.o → code object)
  → Extract AMD_COMGR_DATA_KIND_EXECUTABLE from output data set
  → Return as MemoryBuffer
```

**Dependency model:** Pure dlopen — no build-time dependency on comgr. If
`libamd_comgr.so` is not installed, the plugin still works for native ELF
images; SPIR-V images produce a clear error message:
`"SPIR-V compilation requires AMD comgr library (libamd_comgr.so). Install ROCm to enable SPIR-V support."`

### 8. Build System

**File:** `offload/plugins-nextgen/amdgpu/CMakeLists.txt`

- Added `src/` to include directories (for `ComgrInterface.h`)
- Added `spirv64-amd-amdhsa` to `LIBOMPTARGET_SYSTEM_TARGETS` (for testing)

No new library dependencies — comgr is loaded at runtime.

## Data Flow

```
                    COMPILE TIME
                    ============

  foo.c + -fopenmp --offload-arch=amdgcnspirv
                |
                v
  Driver: inferOffloadToolchains()
    AMDGCNSPIRV → "spirv64-amd-amdhsa"
                |
                v
  getOffloadToolChain()
    OS=AMDHSA + isSPIRV() → SPIRVOpenMPToolChain
                |
                v
  cc1 -triple spirv64-amd-amdhsa
    (OpenMP frontend → LLVM IR → SPIR-V backend → .spv)
                |
                v
  clang-linker-wrapper
    linkDevice() → generic::clang() with spirv64
    → SPIR-V binary embedded in host object
                |
                v
  Host linker → executable with embedded SPIR-V


                    RUNTIME
                    =======

  libomptarget loads plugin (omptarget.rtl.amdgpu)
                |
                v
  GenericDeviceTy::loadBinary()
    identify_magic() == spirv_object
                |
                v
  AMDGPUDeviceTy::compileSPIRVImage()
                |
                v
  ComgrInterface::compileSPIRV(spirv_data, "amdgcn-amd-amdhsa--gfx90a")
    1. TRANSLATE_SPIRV_TO_BC
    2. CODEGEN_BC_TO_RELOCATABLE
    3. LINK_RELOCATABLE_TO_EXECUTABLE
                |
                v
  AMDGPUDeviceImageTy::loadExecutable()
    hsa_code_object_reader_create_from_memory()
    hsa_executable_load_agent_code_object()
                |
                v
  Kernel execution on GPU
```

## Design Decisions

### Why SPIRVOpenMPToolChain instead of AMDGPUOpenMPToolChain?

`AMDGPUOpenMPToolChain` inherits from `ROCMToolChain` which inherits from
`AMDGPUToolChain`. These base classes assume `amdgcn` architecture throughout
(register classes, ISA features, device library paths). Using them with a
`spirv64` triple would require pervasive changes. `SPIRVToolChain` is the
correct base for SPIR-V targets.

### Why dlopen instead of hard-linking comgr?

1. **No build dependency** — upstream LLVM builds don't require ROCm installed
2. **Plugin still works** for native ELF images without comgr
3. **Matches existing pattern** — HSA runtime is also loaded via dlopen
4. **Clear error** when SPIR-V image encountered without comgr

### Why not link AMD device libs at compile time?

AMD device libs (ockl, ocml, etc.) are distributed as AMDGPU bitcode. They
cannot be linked into SPIR-V at compile time because:
1. The bitcode targets `amdgcn` — incompatible with `spirv64`
2. The libs contain GPU-specific intrinsics that have no SPIR-V equivalent
3. comgr links them automatically during the `CODEGEN_BC_TO_RELOCATABLE` step

The only compile-time library is the OpenMP device RTL (already handled).

### Why not change HIP toolchain selection?

`HIPAMDToolChain` handles `spirv64-amd-amdhsa` internally through
special-casing. Changing it to use `HIPSPVToolChain` breaks existing HIP
workflows. The HIP and OpenMP paths have different requirements — HIP's SPIR-V
support was built into `HIPAMDToolChain` while OpenMP's is cleanly separated
into `SPIRVOpenMPToolChain`.

## Open Items

1. **comgr enum values:** The enum values for `amd_comgr_data_kind_t`,
   `amd_comgr_action_kind_t`, etc. are declared based on publicly documented
   values. They should be verified against the actual `amd_comgr.h` header from
   a recent ROCm installation.

2. **Compilation caching:** Runtime SPIR-V compilation adds startup latency.
   A cache keyed by `{SHA256(SPIR-V), ISA name}` could avoid recompilation.
   comgr may have built-in caching; otherwise a file-based cache in
   `$XDG_CACHE_HOME/openmp-spirv/` would work.

3. **OpenMP Device RTL for spirv64:** The device RTL
   (`offload/DeviceRTL/`) must be compilable for `spirv64-amd-amdhsa`. This
   may require adding the triple to the DeviceRTL build configuration and
   resolving SPIR-V-specific issues (atomics, barriers, address spaces).

4. **SPIR-V extensions:** AMD SPIR-V may use vendor extensions
   (e.g., `SPV_AMD_*`). comgr's SPIRV-LLVM-Translator must support these.

5. **Error diagnostics:** comgr can produce diagnostic logs during compilation.
   These should be surfaced to the user when compilation fails (the current
   implementation enables logging via `ActionInfoSetLogging`).

6. **Testing with hardware:** The driver tests verify toolchain selection. Full
   end-to-end testing (compile SPIR-V, runtime comgr compilation, GPU
   execution) requires an AMDGPU device with ROCm and comgr installed.

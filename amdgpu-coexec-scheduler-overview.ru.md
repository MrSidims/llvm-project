# CoExec-планировщик AMDGPU — как он работает, какие задачи решает и с чем борется

Файлы: `llvm/lib/Target/AMDGPU/AMDGPUCoExecSchedStrategy.{h,cpp}`

Документ подробно разбирает co-execution ("совместное исполнение") планировщик AMDGPU: что
это за железная концепция, зачем нужен отдельный планировщик, как он устроен внутри, какие
проблемы решает и с какими сложностями сталкивается. Все ссылки на код даны как `файл:строка`.

---

## 1. Что такое co-execution на уровне железа

На современных матричных GPU AMD (gfx1250 и родственные) есть несколько независимых
исполнительных конвейеров ("hardware units"), которые могут работать **одновременно**:

```
                    ┌─────────────────────────────────────────────┐
                    │                  SIMD / CU                   │
                    │                                              │
   очередь          │   ┌──────────┐   ┌──────────┐   ┌────────┐   │
   инструкций  ───► │   │  Matrix  │   │   VALU   │   │  VMEM  │   │
                    │   │  engine  │   │ (обычн.  │   │ (загр. │   │
                    │   │ WMMA/MFMA│   │  ALU)    │   │ памяти)│   │
                    │   └────┬─────┘   └────┬─────┘   └───┬────┘   │
                    │        │              │             │        │
                    │   долго (N тактов) быстро (1т)   долго (память)│
                    └────────┼──────────────┼─────────────┼────────┘
                             ▼              ▼             ▼
                        одна WMMA держит матричный
                        юнит занятым много тактов ─── а остальные юниты
                                                      в это время могут
                                                      простаивать ИЛИ работать
```

Ключевой факт: **матричная инструкция WMMA/MFMA занимает матричный движок на много
тактов** (десятки тактов), но при этом **не занимает** ни VALU, ни блок доступа к памяти
(VMEM), ни LDS (DS). Пока матричный движок "молотит" одну WMMA, у нас есть **окно
(coexec window)**, в котором железо может параллельно выполнить независимую работу на
других юнитах — загрузить следующий тайл из памяти, посчитать пакованное сложение и т.д.

**Co-execution — это и есть заполнение этого окна полезной работой.** Если планировщик
поставит инструкции неудачно (например, две WMMA подряд, а загрузки памяти "кучей" в
конце), то:

- либо соседние юниты простаивают, пока крутится матрица;
- либо матричный движок простаивает, ожидая, пока подгрузятся данные для следующей WMMA.

Цель — **перекрыть длинную матричную работу независимой работой на других юнитах**, чтобы
конвейеры были заняты одновременно, а не по очереди.

## 2. Какую проблему решает CoExec-планировщик

Стандартный планировщик LLVM (`GenericScheduler` / базовый `GCNSchedStrategy`)
оптимизирует главным образом **латентность критического пути** и **давление на регистры**.
Он не моделирует явно "какой аппаратный юнит сейчас занят и на сколько тактов" и не
старается специально удержать матричный движок постоянно занятым, заполняя окна.

Пример проблемы (реальный, из теста `coexec-sched-effective-stall.mir`). Исходный порядок:

```
%13 = V_WMMA_SCALE_F32_16X16X128 ...   ; WMMA #1 — занимает матрицу на ~15+ тактов
%14 = V_WMMA_SCALE_F32_16X16X128 ...   ; WMMA #2 — ждёт, матрица ещё занята
%11 = GLOBAL_LOAD_DWORDX2 ...          ; загрузка памяти — независима от WMMA
%12 = V_PK_ADD_F32 %11, %11 ...        ; пакованное сложение, зависит от загрузки
```

Если поставить две WMMA подряд, вторая WMMA **упирается в структурный столл**: матричный
движок ещё занят первой. Загрузка памяти и сложение при этом ждут в самом конце, хотя они
не зависят от WMMA и могли бы исполниться **в окне** первой WMMA.

CoExec-планировщик переставляет так, чтобы независимая работа встала в окно матричной
операции. Результат (вывод `-amdgpu-sched-strategy=coexec`):

```
%13 = V_WMMA_SCALE_F32_16X16X128 ...   ; WMMA #1 стартует, открывает окно
%10 = IMPLICIT_DEF (адрес)             ┐
%11 = GLOBAL_LOAD_DWORDX2 %10 ...       │ независимая работа ВНУТРИ окна WMMA #1
%14 = V_WMMA_SCALE_F32_16X16X128 ...   ; WMMA #2 — матрица уже освободилась
%12 = V_PK_ADD_F32 %11, %11 ...        ┘ сложение перекрыто исполнением WMMA #2
```

Загрузка памяти теперь исполняется, пока матричный движок занят WMMA #1, а сложение —
пока он занят WMMA #2. Юниты работают одновременно.

**Итого: задача планировщика — упорядочить инструкции так, чтобы длинные матричные
операции всегда имели рядом независимую работу для заполнения их окон, и наоборот, чтобы
данные для следующей матричной операции были готовы к моменту освобождения движка.**

## 3. Общая архитектура планировщика

`AMDGPUCoExecSchedStrategy` — это подкласс `GCNSchedStrategy`, работающий **строго
сверху вниз** (top-down) на pre-RA стадии (до распределения регистров). Он запускается
поверх `GCNScheduleDAGMILive`.

```
              createGCNCoExecMachineScheduler  (:768)
                          │
                          ▼
          ┌──────────────────────────────────┐
          │      GCNScheduleDAGMILive         │  ← DAG региона, трекеры давления,
          │                                   │    DAG.MBFI (частоты блоков) доступны
          └──────────────┬───────────────────┘
                         владеет
                          ▼
          ┌──────────────────────────────────┐
          │     AMDGPUCoExecSchedStrategy     │
          │  ┌────────────────────────────┐   │
          │  │  CandidateHeuristics Heurs │   │  ← «мозг» coexec-эвристик
          │  │  ┌──────────────────────┐  │   │
          │  │  │ HWUInfo[NUM_FLAVORS] │  │   │  ← по одному ведру на класс юнита
          │  │  └──────────────────────┘  │   │
          │  └────────────────────────────┘   │
          └──────────────────────────────────┘
                          │
       + IGroupLP DAG-мутация (createIGroupLPDAGMutation, :774)
```

Три стадии планирования задаются в конструкторе (`:458-466`):

1. `ILPInitialSchedule` — основной проход с coexec-эвристиками.
2. `RewriteMFMAForm` — стадия переписывания формы MFMA VGPR↔AGPR (см. отдельный отчёт).
3. `PreRARematerialize` — стандартная pre-RA ремат-стадия.

Плюс `UseGCNTrackers = true` (`:465`) — используются более точные GCN-трекеры давления на
регистры.

Только top-down; bottom-up отвергается в `initPolicy` (`:472-478`) ассертом.

## 4. Ключевые абстракции

### 4.1. `InstructionFlavor` — класс аппаратного юнита

Каждая `MachineInstr` относится к одному «вкусу» (flavor) — тому аппаратному юниту, который
она нагружает. Перечисление в `AMDGPUCoExecSchedStrategy.h:28-40`:

| Flavor            | Что это                                 | Открывает окно? |
|-------------------|-----------------------------------------|-----------------|
| `WMMA`            | MFMA / WMMA матричные операции           | **да**          |
| `SingleCycleVALU` | обычная VALU (1 такт)                    | нет             |
| `TRANS`           | трансцендентные (`v_exp`, `v_log`, …)    | **да**          |
| `MultiCycleVALU`  | VALU c repeat rate > 1                   | **да**          |
| `VMEM`            | FLAT / GLOBAL / scratch доступ к памяти  | нет             |
| `DS`              | LDS / GDS                                | нет             |
| `SALU`            | скалярный ALU                            | нет             |
| `DMA`             | LDS DMA                                  | нет             |
| `Fence`           | `S_WAIT_*`, барьеры                      | нет             |
| `Other`           | всё остальное (в т.ч. debug)             | нет             |

Диспетчеризация — `classifyFlavor()` (`:97-132`) через предикаты `SIInstrInfo`
(`isMFMAorWMMA`, `isTRANS`, `isVALU`, `isDS`, `isVMEM`, `isSALU`, …).

**Флаг `ProducesCoexecWindow` выставлен для `{WMMA, MultiCycleVALU, TRANS}`** (`:268-270`).
Именно эти классы занимают юнит на много тактов и потому создают окно, которое можно
заполнить.

### 4.2. `HardwareUnitInfo` (HWUI) — учёт по юниту

На каждый flavor заводится ведро `HardwareUnitInfo` (`.h:154-236`), которое ведёт учёт для
**текущего региона**:

- `AllSUs` — все SUnit'ы региона этого flavor;
- `PrioritySUs` — подмножество, которое хотим планировать первым; выбирается по
  **минимальной глубине** (depth) — естественно для top-down;
- `TotalCycles` — сумма `ReleaseAtCycle` (спрос региона на этот ресурс в тактах);
- `ProducesCoexecWindow` — открывает ли этот класс окно.

```
   HWUInfo[WMMA]   AllSUs = { WMMA#1, WMMA#2 }   TotalCycles = 30   window=✔
                   PrioritySUs = { WMMA#1 }        (мин. depth)
   HWUInfo[VMEM]   AllSUs = { LOAD }              TotalCycles = 20   window=✘
                   PrioritySUs = { LOAD }
   HWUInfo[VALU1c] AllSUs = { PK_ADD }            TotalCycles = 1    window=✘
                   PrioritySUs = { PK_ADD }
```

### 4.3. Жизненный цикл региона

`CandidateHeuristics::initialize()` (`:251-273`) сбрасывает все HWUI, ставит флаги окна и
вызывает `collectHWUIPressure()` (`:275-285`) — классифицирует каждый SU в DAG и вставляет
в нужное ведро. Каждый `insert` (`:160-183`) обновляет `TotalCycles` и, возможно,
пересобирает `PrioritySUs` по глубине.

`schedNode()` (`:490-493`) при коммите каждого SU вызывает `updateForScheduling()`, который
делает `HWUI->markScheduled(SU, cycles)` (`:185-220`): убирает SU из `AllSUs`/`PrioritySUs`,
уменьшает `TotalCycles` и, если приоритетное множество опустело, **пересобирает** его из
оставшихся `AllSUs`.

## 5. Как выбирается следующая инструкция

```
pickNode(IsTopNode)                                  (:495)
  │
  ├─ pickOnlyChoice(Top)      быстрый путь: один кандидат готов  (:88)
  │
  └─ pickNodeFromQueue(Top,…)  иначе — сравнить кандидатов        (:554)
        │
        ├─ обойти Zone.Available   (готовые сейчас)
        └─ затем Zone.Pending      (готовые позже)
              │
              для каждого SU строим SchedCandidate TryCand
              и запускаем tryCandidateCoexec(Cand, TryCand)      (:629)
              если TryCand победил → он становится новым Cand
```

`pickNodeFromQueue` (`:554-600`) сначала обходит `Zone.Available`, затем `Zone.Pending`.
Для каждого SU строится `SchedCandidate` и сравнивается с текущим лучшим (`Cand`) через
`tryCandidateCoexec`. Если победил кандидат из **Pending**, `pickNode` (`:529-540`)
продвигает `Top` (`bumpCycle`) за его ready-такт и мимо оставшихся хазардов, чтобы
остальной планировщик видел согласованное состояние.

## 6. `tryCandidateCoexec` — стек эвристик

Порядок сравнения (первое решающее правило побеждает), `:629-719`:

```
   ┌─ 1. First valid          — инициализировать пустой Cand           (:633)
   ├─ 2. PhysReg bias          — тянуть def/copy физрегов к их стороне   (:639)
   ├─ 3. Excess pressure       — отклонить всё, что превысит лимит RP    (:644)  ← жёсткий барьер
   │      ─────────── далее только если SameBoundary (одна зона) ───────────
   ├─ 4. Effective stall       — tryEffectiveStall: меньший столл в текущем такте (:658)
   ├─ 5. Critical resource     — tryCriticalResource                     (:662)
   ├─ 6. Critical resource dep — tryCriticalResourceDependency           (:667)
   ├─ 7. Cluster successor     — держать кластеры вместе                  (:686)
   ├─ 8. Weak edges            — минимизировать вес слабых рёбер          (:692)
   ├─ 9. Max pressure          — минимизировать RPDelta.CurrentMax        (:698)  ← мягкий барьер RP
   ├─10. Latency               — обычный редуктор латентности            (:706)
   └─11. NodeOrder             — тай-брейк по исходному порядку           (:711)
```

Шаги 3 и 9 — это **давление на регистры** (`RegExcess` жёстко, `RegMax` мягко). Они стоят
рядом с coexec-правилами и не дают эвристикам продавить лимит регистров: любой выбор,
превышающий бюджет, отвергается до того, как coexec-правила получат голос. То есть
coexec-эвристики работают **внутри** бюджета, заданного проверками давления. Именно поэтому
планировщик сам по себе не создаёт нового спилла (см. §9).

### 6.1. Шаг 4 — `tryEffectiveStall` (`:721-766`)

Для каждого кандидата считается «эффективный столл» — сколько тактов будет потрачено
впустую, если поставить его в текущий такт:

```
   Ready      = max(0, SU.TopReadyCycle - CurrCycle)     // ждём готовности операндов
   Structural = getStructuralStallCycles(Zone, SU)       // занят ли нужный юнит
   Latency    = Zone.getLatencyStallCycles(SU)           // латентность по критич. пути
   Effective  = combine(Ready, Structural, Latency)      // по умолчанию max(...)
```

Затем `tryLess(Effective)` — предпочитается кандидат с **меньшим** эффективным столлом
(причина `Stall`). Все три источника считаются взаимозаменяемыми: планировщику неважно
*почему* такт потрачен, важно *сколько* тактов потеряно.

> Именно эта функция — точка приложения текущего патча с настраиваемыми «ручками». Раньше
> `Effective` был жёстко зашит как `max({Ready,Structural,Latency})`; теперь это
> `combineEffectiveStall(...)` с весами и режимом max/sum + допуск `slack`. Подробнее — в
> `amdgpu-coexec-stall-knobs-patch.ru.md`.

Как `Structural` относится к окну: если на матричном юните ещё крутится предыдущая WMMA,
у второй WMMA `Structural` большой (движок занят), а у независимой загрузки памяти
`Structural = 0` — поэтому загрузка «выигрывает» текущий такт и встаёт в окно. Так шаг 4
напрямую реализует заполнение окна.

### 6.2. Шаг 5 — `tryCriticalResource` (`:412-456`)

Сначала `sortHWUIResources()` (`:304-323`) упорядочивает ведра по приоритету:

```
   1. сначала производители окна (WMMA, MultiCycleVALU, TRANS)   producesCoexecWindow()
   2. затем по TotalCycles (более нагруженный юнит — раньше)
   3. затем по size()  ← ВНИМАНИЕ: код предпочитает МЕНЬШЕ инструкций (A.size() < B.size()),
                          а комментарий говорит «prefer more» — вероятный баг (:315-317)
   4. затем по порядку enum flavor
```

Затем для каждого ведра в порядке приоритета:

- если ровно один из `Cand`/`TryCand` потребляет этот юнит — он побеждает (`RegCritical`);
- если оба потребляют, и это `DS` — сначала рекурсия в `tryCriticalResourceDependency`
  (латентности DS велики, поэтому «включатель зависимости» важнее самого потребителя);
- иначе — `HWUI.getHigherPriority(Cand.SU, TryCand.SU)`: кто раньше в `PrioritySUs`, тот и
  побеждает.

### 6.3. Шаг 6 — `tryCriticalResourceDependency` (`:325-410`)

Для каждого ведра ищем **следующую цель** — SU, которую планировщик пытается «накормить»:

```cpp
TargetSU = HWUI.getNextTargetSU(LookDeep);   // (:134-158)
```

`getNextTargetSU`:
- сначала идём по `PrioritySUs`, возвращаем первый ещё-не-готовый;
- если все приоритетные готовы и `LookDeep == false` — возвращаем null;
- если `LookDeep == true` — сканируем `AllSUs` и берём не-готовый SU с минимальной глубиной.

Предикат `LookDeep`:

```cpp
HwType == WMMA && (Cand.flavor ∈ {VMEM, DS} || TryCand.flavor ∈ {VMEM, DS})
```

то есть: «мы пытаемся поставить операцию памяти, пока приоритетный юнит — матрица». В такой
ситуации приоритетные матричные SU обычно ещё на несколько SUnit'ов впереди, поэтому надо
заглянуть за приоритетное множество вглубь `AllSUs`, чтобы увидеть будущего потребителя
матрицы.

Зная `TargetSU`, предпочитаем кандидата, который **на пути к** `TargetSU`
(`DAG->IsReachable(TargetSU, Cand.SU)`):

- включает только один → он и побеждает;
- включают оба → предпочесть больший `getHeight()` (длиннее остаток критического пути);
- ничья → оставить `Cand`.

Это и есть механизм «подготовки данных»: планировщик специально ставит вперёд ту загрузку,
которая является предком будущей матричной операции, чтобы к моменту освобождения движка
данные уже были готовы.

## 7. Производители окна против потребителей — суть «coexec»

`ProducesCoexecWindow` переворачивает порядок приоритета ресурсов так, что планировщик
**намеренно ставит длинную матричную операцию первой**, а затем заполняет получившееся
in-flight окно независимой работой из более дешёвых юнитов (VMEM, DS, SALU), выбирая её по
эвристике зависимостей:

```
   такт →   0        5        10       15       20       25       30
   Matrix   │████████ WMMA#1 ████████│████████ WMMA#2 ████████│
   VMEM     │  ██ LOAD ██                                      │
   VALU     │              ██ PK_ADD ██                        │
                └── окно WMMA#1 ──┘   └── окно WMMA#2 ──┘
```

Это и есть «coexec» в названии: WMMA стартует, и **пока она молотит**, планировщик выбирает
следующую загрузку памяти, которая питает *следующую* WMMA.

## 8. Проблемы, с которыми сталкивается планировщик, и как он их решает

| Проблема | Решение в коде |
|----------|----------------|
| Нужно моделировать занятость юнитов, а базовый планировщик этого не делает | `HardwareUnitInfo` ведёт `TotalCycles` и `PrioritySUs` на каждый flavor (`:154-236`) |
| Готовые кандидаты не открывают окно, а нужный SU ещё не готов | обход не только `Available`, но и `Pending`; `bumpCycle` до готовности (`:529-540`) |
| Согласованность «сначала зависимости, потом сам потребитель» | `PrioritySUs` разделяются между `tryCriticalResource` и `tryCriticalResourceDependency` (комментарий в `.h:156-162`) |
| Длинные цепочки памяти для WMMA не видны через приоритетное множество | `LookDeep`: заглянуть вглубь `AllSUs` при memory-vs-WMMA (`:334-336, 143-157`) |
| Заполнение окна не должно раздувать давление на регистры | жёсткий `RegExcess` (шаг 3) и мягкий `RegMax` (шаг 9) стоят внутри стека (`:644, :698`) |
| Post-RA перепланирование могло бы сломать выстроенный порядок | `GCNNoopPostScheduleDAG` — пустой post-RA DAG (`:77-84, 778-783`) |

### Тонкость: что видно и что не видно до RA

`getStructuralStallCycles` (`GCNSchedStrategy.cpp:277-312`) возвращает
`max(` столл по зарезервированным ресурсам SchedModel `,` wait-states от hazard-recognizer `)`.

- Путь зарезервированных ресурсов (`:287-300`) **активен pre-RA** и ненулевой для WMMA/MFMA
  (матричный юнит зарезервирован на много тактов) — эмпирически `struct=15` для
  `V_WMMA_SCALE_F32_16X16X128` в тесте coexec.
- Путь hazard-recognizer (`:302-309`) — **только post-RA** (`!hasVRegLiveness`), поэтому
  последовательностно-зависимые таблицы wait-state
  (`GCNHazardRecognizer.cpp` `WMMAWaitStates[]={5,9,3,5,9,17}`) pre-RA **не видны**.

Итого: pre-RA рычаг структурного столла работает через зарезервированные ресурсы, но полную
стоимость хазардов планировщик до RA не видит.

## 9. Поведение по спиллу / давлению на регистры

Стратегия **не добавляет** новых механизмов давления. Она прогоняет стандартные проверки
`tryPressure` (`RegExcess` — шаг 3, `RegMax` — шаг 9) в `tryCandidateCoexec`, так что любое
правило, которое продавило бы лимит давления, отвергается ещё до голоса coexec-эвристик.
Coexec-правила работают только внутри бюджета, заданного этими проверками. Это критично для
GPU: occupancy — ступенчатая функция от **пикового** VGPR, и смещение расписания в пользу
«горячего» перекрытия не должно случайно поднять пик и обрушить occupancy всего ядра.

## 10. Пример ассемблера: до и после (из теста)

Регион (MIR-вход, `coexec-sched-effective-stall.mir:52-67`): две WMMA, одна загрузка
памяти и одно пакованное сложение.

**Стандартный планировщик (`DEFAULT`)** — две WMMA идут почти подряд, память и сложение в
конце:

```mir
%13 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 %0, %1, 0, %2, %3, %4, ... ; WMMA #1
%11 = GLOBAL_LOAD_DWORDX2 %5, 0, 0                                 ; загрузка
...                                                                ; defs следующего тайла
%12 = V_PK_ADD_F32 8, %11, 8, %11, ...                            ; сложение
%14 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 %6, %7, 0, %8, %9, %10, .. ; WMMA #2
S_ENDPGM 0, implicit %12, implicit %13, implicit %14
```

**CoExec (`-amdgpu-sched-strategy=coexec`)** — независимая загрузка и сложение задвинуты
**в окна** между двумя WMMA:

```mir
%13 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 %0, %1, 0, %2, %3, %4, ... ; WMMA #1 — открывает окно
...                                                                ; defs операндов WMMA #2
%10 = IMPLICIT_DEF                                                 ; адрес загрузки
%11 = GLOBAL_LOAD_DWORDX2 %10, 0, 0                                ; загрузка В ОКНЕ WMMA #1
%14 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 %5, %6, 0, %7, %8, %9, ... ; WMMA #2
%12 = V_PK_ADD_F32 8, %11, 8, %11, ...                            ; сложение перекрыто WMMA #2
S_ENDPGM 0, implicit %12, implicit %13, implicit %14
```

Логика решения на шаге 4 (`tryEffectiveStall`): когда рассматривается вторая WMMA против
загрузки памяти, у WMMA `Structural ≈ 15` (матрица занята первой WMMA), у загрузки
`Structural = 0`. `Effective(WMMA) = 15 > Effective(LOAD) = 0` → `tryLess` выбирает
загрузку, и она встаёт в окно.

Про инструкцию `V_WMMA_SCALE_F32_16X16X128_F8F6F4`: это масштабируемая WMMA gfx1250,
матричный тайл 16×16 с редукцией по K=128, входы FP8/FP6/FP4, аккумуляция во F32, с
отдельным scale-фактором. На уровне ISA идея та же: одна такая инструкция удерживает
матричный движок много тактов, открывая окно для VMEM/VALU.

## 11. Постскриптум: `GCNNoopPostScheduleDAG`

`createGCNNoopPostMachineScheduler` (`:778-783`) возвращает «ничего не делающий» post-RA
DAG (`:77-84`). Это позволяет AMDGPU-конвейеру отключать post-RA планирование с точностью
до функции для coexec-потока, не трогая остальной бэкенд. Смысл: coexec тщательно выстроил
порядок под окна, и повторное post-RA перепланирование только испортило бы его.

# Авто-тюнинг бэкенд-пути кодогенерации AMDGPU

Исследование авто-тюнинга на **бэкенд-пути** (post-ISel) для AMDGPU, с фокусом на
co-execution планировщике и переписывании формы MFMA VGPR→AGPR, тезисе «обнаружение горячих
циклов снимает пороги», реализуемости PGO на GPU и риске давления на регистры / обрыва
occupancy. Все утверждения снабжены якорями `файл:строка` и перепроверены отдельным
состязательным (adversarial) проходом верификации; правки из него внесены.

> Русская версия отчёта `amdgpu-backend-autotuning.md`. Дополнена блок-схемами и примерами
> ассемблера. Связанные документы: `amdgpu-coexec-scheduler-overview.ru.md` (как устроен
> сам coexec-планировщик) и `amdgpu-coexec-stall-knobs-patch.ru.md` (детали текущего патча).

---

## 0. Кратко (TL;DR)

- **Вердикт по тезису: обоснован и наполовину уже реализован.** Взвешивание по частоте
  блоков (горячим циклам) — легитимный рычаг для обеих подсистем.
  `MachineBlockFrequencyInfo` уже подключён к каждой стадии планировщика, а стадия
  переписывания MFMA *уже* масштабирует свою cost-модель по частоте блока.
  Coexec-планировщик, напротив, полностью частотно-слеп — это чистое «зелёное поле».
- **Честная оговорка: частота *оценочная*, не *измеренная*.** Типичные amdgcn-компиляции не
  несут `branch_weights`/`entry_count`, поэтому BFI берётся из статических эвристик ветвей +
  глубины циклов. Реальные профили с устройства требуют out-of-tree работы (RFC AMD
  «Offload-PGO-for-HIP»), которой **в этом дереве нет**.
- **Опасность давления на регистры реальна и это ключевой момент.** Occupancy на GPU —
  ступенчатая функция от *пикового* использования VGPR по всему ядру. Смещение расписания в
  пользу горячих циклов может перевести пик через границу гранулы и обрушить occupancy для
  *всего* ядра. Любое послабление по горячим циклам обязано быть защищено occupancy-guard'ом.
- **Рекомендуемый путь:** (1) вынести несущие захардкоженные константы в
  сохраняющие-поведение «ручки» + построить внешний перебор флагов на корпусе GEMM;
  (2) заменить грубое целочисленное взвешивание по частоте на существующую схему `FreqInfo`
  и добавить occupancy-guard'ированное послабление в горячих регионах; (3) опциональный
  MLGO-советник. Матричные/GEMM-ядра — идеальная первая цель.

```
   Фаза 1 ─────────────► Фаза 2 ──────────────► Фаза 3
   «ручки» + перебор     частотные эвристики    MLGO-советник
   (мало, низкий риск)   (средне, средний риск) (много, выше риск)
        │                     │                      │
        └── дефолт не меняется └── occupancy-guard     └── только если 1–2
            датасет для ф.3        + FreqInfo             доказали пользу
```

## 1. Поверхность тюнинга бэкенда AMDGPU сегодня

Тюнинг полностью ручной: ~43 `cl::Hidden` `-mllvm` флагов, горстка per-function атрибутов и
замороженные TableGen-константы sched-модели. **Никакого MLGO/autotuning-обвеса к AMDGPU не
подключено** — единственная строка «advisor» в таргете это устаревший комментарий
(`AMDGPURewriteAGPRCopyMFMA.cpp:312`).

**Самая чистая точка входа — выбор стратегии на функцию.**
`GCNTargetMachine::createMachineScheduler` (`AMDGPUTargetMachine.cpp:1357-1385`) резолвит
`getSchedStrategy(F)` (`:592`), который сначала читает **атрибут функции
`amdgpu-sched-strategy`**, затем глобальный `-amdgpu-sched-strategy`. Так как это атрибут
функции, тюнер может назначить разную стратегию каждому ядру без пересборки модуля. Значения:
`max-ilp`, `max-memory-clause`, `iterative-{ilp,minreg,maxocc}`, `coexec`, по умолчанию
MaxOccupancy.

**Открытые скалярные ручки (планировщик):** `-amdgpu-schedule-metric-bias` (10, вес
occupancy-vs-latency), `-amdgpu-vgpr-threshold-percent` (0, масштаб лимитов Excess/Critical
RP), `-amdgpu-scheduler-pending-queue-limit` (256),
`-amdgpu-schedule-relaxed-occupancy`, `-amdgpu-use-amdgpu-trackers`,
`-amdgpu-disable-rewrite-mfma-form-sched-stage` (**true** — см. §3).

**Бюджет occupancy:** атрибуты `amdgpu-num-vgpr` / `-num-sgpr` / `-waves-per-eu` /
`-flat-work-group-size` питают `getMaxNumVGPRs`/`getMaxNumSGPRs`
(`GCNSubtarget.cpp:531,611`). `-amdgpu-membound-threshold` (50),
`-amdgpu-limit-wave-threshold` (50).

**MFMA/матрица:** ранний выбор формы `SIMachineFunctionInfo::selectAGPRFormMFMA`
(`SIMachineFunctionInfo.h:1226`, флаг `-amdgpu-mfma-vgpr-form`, по умолч. false), IGLP
GEMM-коэффициенты чередования захардкожены (`AMDGPUIGroupLP.cpp:1024-1032` DS:2/MFMA:1;
`:2304-2324` VALU:2/DS_READ:4), `-amdgpu-mfma-padding-ratio` (0).
**Программного конвейеризатора нет** — `SIInstrInfo` не реализует
`analyzeLoopForPipelining`, поэтому всё межитерационное перекрытие MFMA берётся из
frontend-unroll + IGLP.

**Заморожено: TableGen sched-модель.** Все счётчики `ProcResource`, размеры буферов и
латентности в `SISchedule.td` (`ReadAdvance<MIMFMARead,-4>` на `:223` и т.д.) — константы на
модель, чьи собственные комментарии признают, что они «Guessed» / «may not be accurate».
Тюнятся только правкой TableGen + пересборкой; наименее реалистичны как рантайм-ручка, но
высокоценная цель для оффлайн-перебора.

## 2. Фокус A — Co-execution планировщик (`AMDGPUCoExecSchedStrategy.cpp`)

Строго top-down, ориентированный на gfx1250 pre-RA планировщик, подкласс `GCNSchedStrategy`.
Работает поверх `GCNScheduleDAGMILive`, так что **`DAG.MBFI` достижим** — тот же handle, что
уже использует стадия переписывания. Моделирует давление по аппаратным юнитам через ведра
`HardwareUnitInfo`, ключ — `InstructionFlavor` (WMMA, SingleCycleVALU, TRANS, MultiCycleVALU,
VMEM, DS, SALU, DMA, …), отслеживая занятые `TotalCycles` и флаг `ProducesCoexecWindow`.

> Полный разбор устройства планировщика — в `amdgpu-coexec-scheduler-overview.ru.md`.

**Он на 100% частотно-слеп и не имеет ни одного `cl::opt` (в исходном виде)** — каждый порог
это литерал или компаратор. (Проверено grep'ом по всему файлу 723 строки.) Текущий патч
(Фаза 1) снимает это для `tryEffectiveStall`.

Места решений, которых коснулись бы тюнер или горячий сигнал:

```
   tryEffectiveStall (:721) ── центральное решение о перекрытии
        Effective = max(Ready, Structural, Latency) → строгий tryLess
        рычаг: веса (wReady,wStruct,wLat) + slack, масштаб slack по горячести
              ↑ уже вынесено текущим патчем

   sortHWUIResources (:304) ── 4-ключевой лексикографический компаратор
        producesCoexecWindow > TotalCycles > size > flavor-enum
        рычаг: линейный скор a·window + b·cycles − c·size + d·bias
              (⚠ баг size-компаратора на :315-317)

   ProducesCoexecWindow set (:268-270) ── {WMMA, MultiCycleVALU, TRANS}
        рычаг: subtarget-битмаска (MultiCycleVALU инертен на gfx950/1250)

   getNextTargetSU / LookDeep (:134-158) ── безграничный min-depth скан
        рычаг: cap MaxLookaheadDepth
```

**Две оговорки честности, всплывшие при верификации:**

1. **Pre-RA компонента `Structural` частично жива (уточнено прототипированием).**
   `getStructuralStallCycles` (`GCNSchedStrategy.cpp:277-312`) возвращает
   `max(` столл по зарезервированным ресурсам SchedModel `,` wait-states hazard-recognizer `)`.
   Путь зарезервированных ресурсов (`:287-300`) **активен pre-RA** и ненулевой для WMMA/MFMA
   (эмпирически `struct=15` для `V_WMMA_SCALE_F32_16X16X128` в тесте coexec). Только путь
   hazard-recognizer (`:302-309`) — post-RA-only (`!hasVRegLiveness`). Итого рычаг
   структурного столла **бьёт** pre-RA через зарезервированные ресурсы — подтверждено
   прототипом Фазы 1. Раннее утверждение «Structural ≈ 0 pre-RA» было преувеличением.
2. **Вероятный баг в компараторе сортировки (`:315-317`):** тай-брейк по размеру использует
   `A.size() < B.size()`, тогда как соседний комментарий говорит «prefer more instructions».
   Код предпочитает *меньше*. Побочно к авто-тюнингу, но стоит отдельной проверки/фикса.

**Выбор — мягкий guard, не жёсткий:** `-amdgpu-sched-strategy=coexec` на не-gfx1250 таргете
выдаёт `DS_Warning` (`diagnoseUnsupportedCoExecSchedulerSelection`,
`AMDGPUTargetMachine.cpp:604-612`), но **всё равно ставит coexec-планировщик** (`:1379-1382`).
Полезно для экспериментов на gfx942/gfx950.

### Пример ассемблера (эффект coexec)

Регион из `coexec-sched-effective-stall.mir`: две WMMA + независимая загрузка + сложение.

```mir
; DEFAULT — две WMMA почти подряд, память/сложение в конце
%13 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 ...   ; WMMA #1
%11 = GLOBAL_LOAD_DWORDX2 ...
%12 = V_PK_ADD_F32 %11, %11 ...
%14 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 ...   ; WMMA #2

; COEXEC — загрузка и сложение задвинуты в окна между WMMA
%13 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 ...   ; WMMA #1 открывает окно
%11 = GLOBAL_LOAD_DWORDX2 %10 ...             ; загрузка В окне WMMA #1
%14 = V_WMMA_SCALE_F32_16X16X128_F8F6F4 ...   ; WMMA #2
%12 = V_PK_ADD_F32 %11, %11 ...               ; сложение перекрыто WMMA #2
```

## 3. Фокус B — переписывание формы MFMA VGPR↔AGPR (`RewriteMFMAFormStage`)

Стадия планирования на всю функцию, которая спекулятивно переклассифицирует регистры
def/src2 у MFMA из VGPR- в AGPR-форму, оценивает стоимость и оставляет изменение, только если
оно чисто выгодно. Трёхслойная воронка:

```
   Слой 1 — допустимость (initGCNSchedStage, ~:1385-1396)
     ├─ !ST.hasGFX90AInsts()                         → пропуск
     ├─ MFI.getMinWavesPerEU() > 1                   → пропуск (захардкожено 1)
     └─ PressureBefore.getArchVGPRNum() > 256 (:1392)→ ТРИГГЕР (только если уже спиллим ArchVGPR)
                                                        нет входа по горячести!

   Слой 2 — легальность (isRewriteCandidate :2352, isReachingDefAGPRForm :2297,
             hasUseRequiringVGPR :2310)  ── фильтры корректности (PR #200972). Не цель тюнинга.

   Слой 3 — cost-модель (getRewriteCost :2472-2572; решение if (Cost>0) return false :1409)
     ├─ SpillCost = (SpillAfter − SpillBefore) * 2   (:2516) ── ×2 самая несущая константа
     ├─ all-or-nothing bail (:2525-2528)             ── один холодный регион ветит всю функцию
     └─ CopyCost = getCopyCost() * (BlockFreq/EntryFreq) (:2543-2563)
```

**Стадия уже частотно-осведомлена — но грубо (с уточнением точности).** `getRewriteCost`
читает `DAG.MBFI` (`:2476`) и масштабирует стоимость в двух местах, оба — потерянное
целочисленное деление, но по-разному:

- Масштаб спилла (`:2508-2522`): `RelativeFreq = больший/меньший из {EntryFreq, BlockFreq}`,
  всегда `≥ 1`. Его потеря — это **мёртвая зона**: любой блок в пределах ~2× от частоты входа
  схлопывается в `RelativeFreq = 1` (без масштаба).
- Масштаб копий (`:2545-2557`): `DefFreq/UseFreq = BlockFreq/EntryFreq` **обнуляется** для
  любого блока холоднее входа — стоимость копий холодных блоков исчезает целиком. *(Это и есть
  настоящая точка «quantize-to-0»; синтез сначала ошибочно указал на путь спилла — исправлено.)*

**Почему выключено по умолчанию.** `DisableRewriteMFMAFormSchedStage` = `cl::init(true)`
(`:102-104`); стадия попадает в конвейер только при флипе флага (`:786-787`). Изменение
«включить по умолчанию» было откачено (`ca5bc14df131`, #185604), т.к. оно «ломает пару
тестов / кейсов downstream». Грубый триггер по addressable-ArchVGPR, захардкоженный ×2,
all-or-nothing bail и грубое целочисленное взвешивание по частоте — ровно та хрупкость,
которую убрала бы горячесть-осведомлённая, occupancy-guard'ированная cost-модель.

## 4. Тезис о горячих циклах — строгий вердикт

**Обоснован, с оговоркой по области применимости.** Механизм реален и частично реализован:

1. **BFI бесплатно доступен везде в планировщике.** `MachineSchedulerLegacy` /
   `PostMachineSchedulerLegacy` делают
   `addRequired<MachineBlockFrequencyInfoWrapperPass>` (`MachineScheduler.cpp:419,435,454`),
   протянуто в `MachineSchedContext::MBFI`, захвачено `ScheduleDAGMILive`, унаследовано как
   `GCNScheduleDAGMILive::DAG.MBFI`. И coexec, и стадия переписывания достают его без новой
   обвязки пассов.
2. **Шаблон для повторного использования уже есть.**
   `PreRARematStage::ScoredRemat::FreqInfo` (`GCNSchedStrategy.h:581-591`, ctor `:2987-3016`)
   строит *свой* `MachineBlockFrequencyInfo(MF, MBPI, *DAG.MLI)` на стеке — самодостаточно,
   без регистрации анализа — хранит per-region масштабированные uint64-частоты с защитой от
   переполнения `ScaleFactor²` и питает `ScoredRemat::operator<`. **Это правильная модель для
   копирования:** она сохраняет дробную горячесть вместо схлопывания в 0/1, как текущая
   cost-модель переписывания.
3. **Где применимо конкретно:**
   - *Переписывание:* заменить грубое целочисленное масштабирование
     (`:2508-2522, 2545-2557`) схемой `FreqInfo`; опционально добавить член горячести в
     триггер (`:1392`); смягчить all-or-nothing bail (`:2525`) в частотно-взвешенный
     глобальный баланс.
   - *Coexec:* посчитать per-region горячесть = `MBFI->getBlockFreq(BB)/getEntryFreq()`
     один раз в `initialize()`/`initPolicy`, затем поднимать slack `tryEffectiveStall` и
     ослаблять сравнение `RegMax` **только в горячих регионах**.

**Два честных ограничения:**
- **«Снятие порогов» хорошо ровно настолько, насколько хорош питающий BFI.** Статический BFI
  разумен для *структурной* частоты цикл-гнёзд, но может сильно ошибаться на дивергентном GPU
  control-flow (нет `!prof`; `getBlockProfileCount` вернёт `nullopt`). Смягчение: взвешивать
  по структурной частоте циклов, а не по перекосу веток. Для GEMM этого достаточно (внутренний
  цикл доминирует).
- **Pre-RA оговорка про структуру (§2, уточнено).** Pre-RA компонента Structural ненулевая
  через зарезервированные ресурсы SchedModel, так что рычаг столла бьёт — но
  последовательностно-зависимые wait-state хазарды всё ещё post-RA-only, значит pre-RA тюнинг
  ловит давление зарезервированных ресурсов, а не полную стоимость хазардов.

## 5. Давление на регистры и обрыв occupancy — центральный риск

Это собственная тревога пользователя, и она подтверждается. Обосновано реальным кодом.

**Occupancy — ступенчатая функция *пикового* использования VGPR:**
```
waves = min( max( TotalNumVGPRs / alignTo(NumVGPRs, Granule), 1), MaxWaves )
```
(`AMDGPUBaseInfo.cpp:1469-1476`). Для gfx90a/gfx942/gfx950 (`FeatureGFX90AInsts`):
`Granule = 8`, `TotalNumVGPRs = 512`. Значит occupancy = `512 / roundup8(peakVGPR)`, с
клампом. Пересечение границы-8, меняющее этот пол, роняет целую волну:

```
   peak VGPR (после roundup8) │ waves/EU
   ───────────────────────────┼──────────
        ≤ 64                   │   8
        ≤ 72                   │   7   ◄── +8 регистров = −1 волна
        ≤ 80                   │   6
        ≤ 96                   │   5
        ≤ 128                  │   4
```

**Обрыв — на уровне ядра, не блока.** `GCNRegPressure::getOccupancy`
(`GCNRegPressure.h:98-103`) берёт *максимум* давления по всей функции. Поэтому расписание,
смещённое в пользу горячего цикла и поднявшее пик VGPR в одном регионе, **роняет occupancy
всего ядра — включая холодный код, которому лишние регистры не нужны.** Выигрыш латентности в
горячем цикле может быть стёрт потерей волны везде. Именно поэтому наивное «трать RP там, где
горячо» опасно на GPU.

**Нюанс AGPR (зачем существует стадия переписывания).** На gfx90a+ файл регистров
*унифицирован*: 512 всего VGPR на arch+acc, но ArchVGPR ограничены адресуемым потолком 256
(`getAddressableNumArchVGPRs`, `AMDGPUBaseInfo.cpp:1440-1445`). Унифицированный счёт =
`alignTo(arch+avgpr, 4) + agpr` (`getUnifiedVGPRNum`, `GCNRegPressure.h:74-82`).
Переписывание срабатывает на `getArchVGPRNum() > 256` (`:1392`): ArchVGPR *спиллят*, пока acc
половина простаивает — перенос операндов MFMA в AGPR снимает arch-подлимит, не увеличивая
унифицированные 512. Так AGPR-переписывание — один из немногих RP-ходов, который может
*поднять* эффективную ёмкость, а не просто переложить давление. Поэтому его стоит делать
правильно, и поэтому горячесть-взвешивание место в его cost-модели.

**`getVGPRSpills` (`GCNRegPressure.h:105-126`)** — оракул моделируемого спилла, который
стадия переписывания уже опрашивает: `max(UnifiedSpill, ArchSpill + AGPRSpill)` против трёх
subtarget-порогов. Естественное жёсткое вето для любого горячего послабления.

**Обязательные ограждения для любого послабления Фазы 2:**
1. **Occupancy-монотонность** — никогда не принимать горячее послабление, которое роняет
   `getOccupancy()` функции. Проверять *следующую границу гранулы*, не только текущее давление.
2. **Вето по числу спиллов** — переиспользовать `getVGPRSpills`: если послабление растит
   моделируемые спиллы в горячем блоке — отклонить.
3. **Только структурная частота циклов** на дивергентном control-flow.
4. **Сохраняющие-дефолт ручки** — каждый новый `cl::opt` по умолчанию = текущее поведение;
   перебор opt-in и не может ухудшить дефолтную сборку.

## 6. Стоимость MFMA в анроллере — учитывается ли матрица?

Прямое продолжение §5: единственное место, где анролл × регистровый след аккумулятора
может пробить occupancy-обрыв — это горячий матричный цикл. Здесь важно понять, **видит ли
дефолтный LLVM-анроллер матричные операции вообще.**

**Короткий вывод: MFMA/WMMA-интринсики учитываются только тривиально — как «одна дешёвая
инструкция» со стоимостью `TCC_Basic = 1`.** MFMA-специфичной логики в анроллере AMDGPU нет:
grep по `mfma|wmma|matrix` во всём `AMDGPUTargetTransformInfo.cpp` возвращает пусто.
`getUnrollingPreferences` (`:114-275`) рассуждает только про GEP/alloca/LDS/ветвления — про
матрицу ни слова.

### Путь стоимости

```
   LoopUnrollPass
     │
     ├─ UnrollCostEstimator (LoopUnrollPass.cpp:681)
     │     LoopSize = CodeMetrics.NumInsts
     │        └─ CodeMetrics.cpp:212 :  NumInsts += getInstructionCost(I, TCK_CodeSize)
     │     → сравнивается с UP.Threshold (=300, AMDGPUTargetTransformInfo.cpp:119)
     │       для partial / runtime анролла              ← метрика размера = CODE SIZE
     │
     └─ analyzeLoopUnrollCost (только full-unroll, LoopUnrollPass.cpp:403)
           getInstructionCost(I, TCK_SizeAndLatency)    ← якобы latency-aware
                 │
                 call к интринсику (TargetTransformInfoImpl.h:1483):
                 → GCNTTIImpl::getIntrinsicInstrCost (AMDGPUTargetTransformInfo.cpp:714)
                     нет case для MFMA → :869-870
                     → BaseT::getIntrinsicInstrCost (BasicTTIImpl.h:1760)
                         if (isTargetIntrinsic(IID)) return TCC_Basic;   (:1770-1771)
                                                          ▲
                              llvm.amdgcn.mfma.* / .wmma.* — target intrinsic → 1
```

### Два следствия из `BasicTTIImpl.h:1770`

1. **Возврат `TCC_Basic` происходит ДО любой логики по cost-kind.** Значит MFMA стоит `1`
   для *всех* видов стоимости — и `TCK_CodeSize`, и `TCK_SizeAndLatency`. Поэтому **даже
   latency-aware путь full-unroll не видит латентности MFMA** — для него она бесплатна, как
   `add` (`TCC_Basic` = «стоимость типичного add», `TargetTransformInfo.h:358`).
2. Единственная поверхность, которую AMDGPU настраивает для анролла
   (`getUnrollingPreferences`), матрицу не упоминает, и при этом бэкенд максимально
   «анролл-охоч»: `UP.MaxCount = UINT_MAX` (`:120`), `Partial = true` (`:121`),
   `Runtime = true` (`:132`), порог 300.

Итог: **GEMM-цикл с 8 MFMA + загрузками весит для анроллера ~20-40 «единиц размера» — глубоко
под порогом 300 → анроллится щедро, не подозревая ни про латентность матрицы, ни про её
регистровый след.**

### Должно ли учитываться? — раздельно по двум осям

**По латентности — скорее нет.** Латентность MFMA не должна тормозить анролл; наоборот, смысл
анролла матричного цикла — вскрыть *независимые* MFMA, чтобы coexec-планировщик / IGLP их
перекрыли (те самые окна из `amdgpu-coexec-scheduler-overview.ru.md`). Недоучёт «MFMA = 1»
здесь случайно работает в нужную сторону: матрица не раздувает размер цикла → анролл идёт
свободно. Кросс-итерационное перекрытие всё равно делается позже планировщиком, не анроллером.

**По давлению на регистры — да, аргумент весомый, и он бьёт прямо в occupancy-обрыв §5.**
- Аккумулятор одной MFMA — это много регистров: от 4 VGPR (16×16 тайл) до 16+ VGPR/AGPR
  (32×32 тайлы). Стоимость `1` для операции, которая *определяет* 4-16 регистров,
  катастрофически недооценивает её регистровый след.
- Порог анролла — косвенный **прокси регистрового давления** (кроме alloca/LDS-бустов
  `:198-231`, RP напрямую анроллер не считает). При «MFMA = 1» прокси врёт: анроллер может
  размножить цикл с уже многими живыми аккумуляторами, пик VGPR перелезет границу гранулы-8
  → потеря волны на **всём** ядре.
- Специального тормоза на этот случай нет: для alloca/LDS бусты есть
  (`UnrollThresholdPrivate/Local`), для аккумуляторов MFMA — ничего.

**Практическая оговорка.** Для реально важных GEMM-ядер анролл обычно уже сделан
**фронтендом** (Triton/rocMLIR разворачивают до lowering либо шлют
`llvm.loop.unroll.count` / `amdgpu.loop.unroll.threshold`-метадату, которую AMDGPU читает на
`:141`). Бэкенд-анроллер для них — вторичный игрок, поэтому радиус MFMA-осведомлённости в
`getUnrollingPreferences` ограничен. Регистровое давление частично ловится реактивно ниже
(RP-трекеры планировщика, `RewriteMFMAForm`, occupancy-based remat) — но это лечение по факту,
а не профилактика.

### Пример: анролл множит аккумуляторы

```
   до анролла (1 итерация)                 ×4 анролл БЕЗ occupancy-guard
   ─────────────────────────               ──────────────────────────────
   loop:                                    loop:
     acc = mfma(a, b, acc)  ; +N VGPR         acc0 = mfma(a0,b0,acc0)  ; +N
     ...                                       acc1 = mfma(a1,b1,acc1)  ; +N
   ; размер для анроллера ≈ 1                 acc2 = mfma(a2,b2,acc2)  ; +N
                                              acc3 = mfma(a3,b3,acc3)  ; +N
                                            ; размер ≈ 4, НО живых VGPR ≈ 4·N
                                            ; anroller видит «4», не «4·N» → может
                                            ; перелезть гранулу и уронить occupancy
```

### Куда бы это встроилось

Тот же `getUnrollingPreferences` (`:159-274`), в существующий обход тела цикла, по образцу
alloca/LDS-эвристик — но тормозом по occupancy, не латентностным штрафом:

```
   при обходе тела: если I — MFMA/WMMA:
     accVGPR += число регистров-аккумуляторов дефа I
   после обхода:
     если alignTo(baseVGPR + accVGPR * UnrollFactor, 8) роняет getOccupancy():
        ограничить UP.MaxCount, чтобы пик не пересёк границу гранулы   ← occupancy-guard §5
     иначе (есть запас пикового VGPR):
        оставить щедрый анролл — перекрытие MFMA полезно
```

Это ровно тот же принцип, что мандаторные ограждения Фазы 2 (§5): **occupancy-монотонность
как тормоз, а не латентностный штраф.** Тема прямо ложится в связку «профилирование →
регистровое давление» из исходного исследования: горячий матричный цикл — единственное место,
где анролл × регистровый след аккумулятора пробивает occupancy-cliff, и там недоучёт
«MFMA = 1» самый вредный.

## 7. Реализуемость PGO на GPU

- **Оценочный BFI (сегодня):** высокая реализуемость, нулевая стоимость, но числа — догадки.
  Любое частотно-осведомлённое coexec/rewrite изменение, построенное сейчас, работает на
  оценках и *авто-обновится* до измеренных частот, если реальные профили когда-нибудь
  появятся — без изменений со стороны планировщика.
- **Реальные профили с устройства (НЕ в этом дереве):** единственный конкретный путь —
  out-of-tree RFC AMD «Offload PGO for HIP»: device-инструментирование через
  `llvm.instrprof.increment`, wave-агрегированные счётчики, host-side извлечение `.profraw`,
  `-fprofile-use` → IR `branch_weights`/`entry_count` → MBFI реконструирует измеренные
  частоты. Проверено, что здесь отсутствует. API неустоявшийся →
  **рассматривать как будущий апгрейд, не как зависимость.**
- **Сэмплирование (rocprof / PC-sampling):** доступно, но **нет пути AutoFDO-ingestion для
  amdgcn** (нет эквивалента `llvm-profgen` с корректным маппингом debug-line amdgcn). Может
  информировать человека, крутящего ручки; автоматически в MBFI не протягивается. Низкая
  реализуемость.

## 8. Матричные/GEMM-ядра как идеальная первая цель? Да.

- **Обнаружение горячих циклов почти бесплатно и однозначно** — цепочечный MFMA GEMM имеет
  один внутренний цикл, тривиально самый горячий; даже оценочный loop-depth BFI ранжирует его
  верно, обходя слабость дивергентных веток.
- **Изучаемые подсистемы матрично-специфичны** — RewriteMFMAForm существует ради формы
  AGPR/VGPR у MFMA; производители coexec-окна — WMMA/MFMA; IGLP GEMM-стратегии — рычаг
  пропускной способности. Матрично-специфичное гейтирование сдерживает радиус поражения и
  может снять возражение «выключено по умолчанию» для RewriteMFMAForm.
- **Награда измерима на рантайме** — форма AGPR-vs-VGPR, IGLP-коэффициенты и padding дают
  измеримые дельты occupancy/пропускной способности.
- *Оговорка:* захардкоженные IGLP-коэффициенты могут быть настроены под конкретную форму
  gfx942 и плохо служить gfx950 или attention (softmax/exp) циклам. Первая цель:
  **gfx942/gfx950 GEMM**, attention — быстрым следующим шагом.

## 9. Предшествующие работы / новизна

- **LLVM MLGO поставляет всего два советника** — inlining-for-size (`MLInlineAdvisor`) и
  regalloc eviction/priority (`MLRegAllocEvictAdvisor`). **Советника MachineScheduler в дереве
  нет.** Советник coexec/rewrite был бы *первым советником планировщика* и *первым по
  эвристикам бэкенда AMDGPU*.
- **Поисковые авто-тюнеры** (OpenTuner, CompilerGym `llvm-ic-v0`, Google `ml-compiler-opt`)
  тюнят порядок пассов / `-mllvm` / `-O` на **гранулярности модуля**, не отдельные post-ISel
  решения эвристик.
- **Авто-тюнеры GPU-ядер** (Triton `@triton.autotune`, rocMLIR/MIGraphX, TVM/Ansor) тюнят
  размеры тайлов / num_warps / num_stages / layouts на **MLIR/frontend/шаблонном слое**, затем
  отдают готовый IR бэкенду. **Никто не тюнит эвристики планировщика/regalloc бэкенда LLVM.**
- **Ближайший аналог: CuAsmRL (CGO 2025)** — RL-планирование NVIDIA **SASS** (post-assembly).
  Это предложение отличается тем, что работает **внутри компилятора на MIR** — портируемо,
  интегрированно и профиль-осведомлённо через уже подключённый BFI.
- **Предсказуемое возражение рецензента:** *«эвристика норм, просто автотюньте ручки»*. Именно
  поэтому Фаза 1 (перебор ручек) идёт первой — она снимает большую часть выгоды дёшево и даёт
  доказательства для чего-то более тяжёлого.

## 11. Побочные находки (стоят отдельных фиксов)
- **Тай-брейк по размеру в `sortHWUIResources` (`:315-317`)** использует `A.size() < B.size()`,

- **Pre-RA coexec-выбор видит столлы зарезервированных ресурсов, но не хазард-wait-states**

  последовательностно-зависимые coexec wait-state таблицы — нет. Стоит проектной заметки.
- **Множитель спилла ×2 (`:2516`)** может быть плейсхолдером; его перебор (Фаза 1) — самый

## 13. Глоссарий

Краткие пояснения терминов, встречающихся в документе. MFMA/WMMA, VGPR/SGPR и общие понятия
GPU предполагаются известными.

### Планирование и co-execution

- **pre-RA / post-RA** — стадия относительно распределения регистров (Register Allocation).
  *Pre-RA* — до RA, оперирует виртуальными регистрами; *post-RA* — после, оперирует
  физическими. Coexec-планировщик работает pre-RA, поэтому видит не всё (см. §2, каветы).
- **регион (region)** — участок базового блока, который планировщик обрабатывает за один
  проход; для него строится свой DAG зависимостей.
- **DAG / SUnit** — граф зависимостей инструкций региона (Directed Acyclic Graph) и его узел
  (Scheduling Unit) — обёртка над `MachineInstr` с глубиной (depth), высотой (height) и
  рёбрами зависимостей.
- **top-down / bottom-up** — направление планирования: сверху вниз (от начала региона) или
  снизу вверх. Coexec-планировщик — строго top-down.
- **SchedCandidate** — кандидат на постановку следующим; `tryLess`/`tryGreater` — примитивы
  сравнения двух кандидатов по одному признаку, задающие причину (Reason) выбора.
- **tryEffectiveStall** — центральное правило coexec: считает «эффективный столл» кандидата
  `combine(Ready, Structural, Latency)` и предпочитает того, кто теряет меньше тактов в
  текущем такте. Именно эту функцию делает настраиваемой текущий патч.
- **ready / structural / latency stall** — три источника простоя. *Ready* — операнды ещё не
  готовы; *structural* — нужный аппаратный юнит занят (зарезервирован); *latency* — задержка
  по критическому пути.
- **coexec window (окно совместного исполнения)** — интервал, пока длинная операция (WMMA,
  TRANS, multi-cycle VALU) занимает свой юнит, а другие юниты свободны для независимой работы.
- **InstructionFlavor** — грубая классификация инструкции по аппаратному юниту, который она
  нагружает (WMMA, VMEM, DS, SALU, …).
- **HardwareUnitInfo (HWUI)** — ведро учёта на один flavor: список SU, суммарные занятые
  такты (`TotalCycles`) и флаг `ProducesCoexecWindow` (открывает ли класс окно).
- **sortHWUIResources / tryCriticalResource / tryCriticalResourceDependency** — эвристики
  выбора: сортировка юнитов по приоритету, затем предпочтение кандидата на самом нагруженном
  юните и кандидата-предка будущего потребителя матрицы (подготовка данных к окну).
- **hazard / wait-states** — аппаратные задержки между зависимыми инструкциями (напр. после
  WMMA), кодируемые таблицами wait-state; полностью видны только post-RA.
- **IGLP (InstructionGroupLP)** — DAG-мутация, группирующая инструкции (напр. чередование
  DS/MFMA в GEMM) для лучшего перекрытия; коэффициенты захардкожены.

### Регистры и occupancy

- **occupancy / waves per EU** — сколько волн (wavefront) одновременно живёт на исполнительном
  юните (EU). Выше occupancy → лучше сокрытие латентности. Ступенчатая функция от пикового
  использования регистров.
- **гранула (allocation granule)** — квант выделения регистров (для gfx90a+ — 8 VGPR).
  Пиковое использование округляется вверх до гранулы; пересечение границы гранулы меняет
  число волн.
- **occupancy cliff (обрыв occupancy)** — резкая потеря целой волны при переходе пика VGPR
  через границу гранулы; считается по *максимуму* давления на всю функцию, поэтому бьёт по
  всему ядру, а не по одному региону (§5).
- **ArchVGPR / AGPR / unified VGPR file** — на gfx90a+ файл регистров унифицирован (512
  всего), но обычные ArchVGPR ограничены адресуемым потолком 256; AGPR (accumulator) — вторая
  половина, доступная матричным операциям. Перенос операндов MFMA в AGPR снимает arch-подлимит.
- **spill (спилл)** — вытеснение регистра в память при нехватке; на GPU дорого и роняет
  производительность. `getVGPRSpills` — оракул моделируемого спилла.
- **register pressure (RP) / RegExcess / RegMax** — давление на регистры; `RegExcess` —
  жёсткий барьер (превышение лимита), `RegMax` — мягкий (рост пикового максимума региона).
- **RewriteMFMAFormStage** — стадия, спекулятивно переписывающая форму операндов MFMA
  VGPR↔AGPR ради снятия давления; выключена по умолчанию, уже частотно-осведомлена (§3).

### Стоимость инструкций и анролл

- **TTI (TargetTransformInfo)** — таргето-зависимая cost-модель; для AMDGPU реализована в
  `AMDGPUTargetTransformInfo.cpp` (классы `AMDGPUTTIImpl` / `GCNTTIImpl`).
- **getInstructionCost** — сколько «стоит» инструкция для данного вида стоимости (cost kind).
- **TCK_CodeSize / TCK_SizeAndLatency** — виды стоимости: чистый размер кода vs размер плюс
  латентность. Размер цикла для порога анролла считается по `TCK_CodeSize`.
- **TCC_Basic / TCC_Free** — базовые кванты стоимости: `TCC_Free = 0` (свернётся при
  lowering), `TCC_Basic = 1` («стоимость типичного add»). MFMA как target intrinsic получает
  `TCC_Basic` независимо от cost kind (§6).
- **target intrinsic** — интринсик, специфичный для таргета (`llvm.amdgcn.*`), в отличие от
  таргето-независимого (`llvm.fma` и т.п.).
- **getUnrollingPreferences** — таргетный хук, задающий политику анролла: порог
  (`UP.Threshold`), partial/runtime-режимы, `MaxCount`. Для AMDGPU рассуждает про
  GEP/alloca/LDS/ветвления, но не про матрицу (§6).
- **partial / runtime unroll** — частичный анролл (на фиксированный множитель) и анролл при
  неизвестном на этапе компиляции числе итераций (с remainder-циклом).
- **CodeMetrics** — утилита, суммирующая размер базового блока через `getInstructionCost` с
  `TCK_CodeSize`; даёт `LoopSize` для анроллера.

### Частоты блоков и профилирование

- **BFI (MachineBlockFrequencyInfo)** — относительная частота исполнения блоков. *Estimated*
  (оценочная) — из статических эвристик ветвей и глубины циклов; *measured* (измеренная) — из
  реального профиля. В amdgcn обычно только оценочная.
- **branch_weights / entry_count** — IR-метаданные профиля, из которых MBFI реконструирует
  измеренные частоты; в типичных amdgcn-компиляциях отсутствуют.
- **FreqInfo** — существующая в `PreRARematStage` схема, хранящая дробную горячесть региона с
  защитой от переполнения; рекомендуемый шаблон для частотно-осведомлённых эвристик (§4).

### Авто-тюнинг и инфраструктура

- **cl::opt / -mllvm / cl::Hidden** — механизм флагов LLVM: `cl::opt` объявляет флаг,
  передаётся через `-mllvm -флаг=значение`, `cl::Hidden` прячет из обычной справки. Основная
  поверхность ручного тюнинга бэкенда.
- **per-function attribute** — атрибут функции (напр. `amdgpu-sched-strategy`,
  `amdgpu-waves-per-eu`), позволяющий задать поведение на отдельное ядро без пересборки модуля.
- **MLGO / advisor** — ML-Guided Optimizations: вынос эвристики за «советника» (advisor) с
  фичами и наградой; в дереве есть только для inlining и regalloc, для планировщика — нет.
- **PGO / AutoFDO** — Profile-Guided Optimizations (по инструментированию) и Automatic Feedback
  Directed Optimization (по сэмплированию); для amdgcn путь ingest'а профиля в MBFI пока
  отсутствует в дереве.
- **OpenTuner / CompilerGym** — внешние поисковые обвесы авто-тюнинга; в Фазе 1 предлагаются
  как обёртка вокруг `llc`/`clang` для перебора флагов по корпусу GEMM.
